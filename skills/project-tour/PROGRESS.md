# project-tour · 开发进度

## 背景

当前的开发实践里有两种极端：**纯 vibe coding** 近似许愿，可控性过差（你只是在描述你想要什么）；**逐行读源码**效率过低且多数时候没必要。缺的是一种**中间态呈现**——既能梳理清楚整体结构，又能在必要时把任意一级的逻辑弄明白。

更进一步的判断：**从逻辑而非具体实现上理解一段代码/模块/功能，是更关键的事**。一个框架或算法的本质是抽象的、逻辑的，只有到实现层面才与语言相关。同一个"排序"意图可以由不同算法实现，同一算法又可以用不同语言承载；站在足够高的抽象层级上，我们只是想在某处实现一个叫"排序"的操作。因此在纯抽象逻辑层面理解"最终呈现之状态的源流"，重要性已远大于理解"在某种具体环境约束下如何实现该逻辑"。

目标读者因此是：**哪怕不熟悉具体编码规则，但具备良好抽象思维与逻辑推理能力的人**。

## 目标（三层，递进）

1. **读** —— 为项目生成分层、可展开的阅读导览。（当前阶段）
2. **重建** —— 在纯逻辑/语义层面可复现、可构建：一份足够好的导览，本身就应是一份能据以重建该系统的构建指导。
3. **改** —— 基于第 2 层派生：能重建，才有资格谈如何修改。产出"逻辑上确定、实施中不确定"的开发指导（不论下游是 vibe coding 还是人类程序员）。

## 当前进度

**第 1 层（读）的基线已成型**，见 `SKILL.md`；`examples/sample-tour.md` 为虚构示例。

导览节点固定四小节：**一、这是什么 / 二、拓扑结构 / 三、交互逻辑 / 四、名称对照表**。原子节点唯一例外：第三小节改称 **三、实现思路**。

小节内的字段名同样固定：拓扑结构含 **宏观结构**、**值得留意**；交互逻辑含 **逐步讲解**、**设计优势**、**易误导概念**。

### 已确定的设计判据

- **结构是因，功能是果** —— 项目之所以能实现目标源于其结构；故拓扑是第一要素。只描述功能而不描述结构，等于讲结果却隐瞒原因。
- **小节名与字段名是固定 schema，不是行文标题** —— 一律用原词，不得改写成"各部分如何交互""它用什么办法做到"这类口语句子。理由有三：① 稳定复用——示例可直接当模板，照搬骨架、重写内容；② 可机检——固定字段使"四小节是否齐备"成为确定性检查项，直接服务下方"基线复现性验证"；③ 抗漂移——口语标题每次生成措辞都不同，读者与工具都无法据此对齐。
- **树沿"组成"向下，依赖是层内的边** —— 把依赖当父子会让树退化成单链，丢失结构。因此树宽而浅，任意部分离根一跳，**按名随机访问**，不必逐级遍历。
- **边标签自述，图类型按需声明** —— 边标签写清"这条边上发生什么"即已自述语义，无需再补一句"边的语义：数据流"（同义反复）。但**关系类型是整张图的属性，无法从单条边读出**：同一组节点按依赖画与按数据流画，方向可能相反。故一张图只用一种关系类型；存在误读风险时（同层多张图、或本图并非按依赖组织）须在图前点明，否则不必赘述。
- **拓扑节点标注真实名称 + 功能角色** —— 单给角色名会漂移，单给真名不易理解。
- **宏观结构逐节点如实命名，不套预设模板** —— 槽位可以普遍化（零信息损失），内容必须特殊化（普遍化即损失）。
- **没有连线也是信息** —— 两部分之间的断开常是关键设计事实，写入"值得留意"。
- **拓扑退化即原子** —— 不由若干部分构成、无边可画时递归结束：拓扑结构小节保留并写明"不存在显式拓扑结构"，第三小节改称"实现思路"。这是结构事实，比主观判断更硬。
- **费曼式表述** —— 默认读者不了解实现、也不了解术语；agent 是讲述者，要让读者仅凭讲述就能在脑中重建，并理解为何这样设计是合理的。
- **名称不回避，而是就地绑定** —— 唯一目标是"讲清楚生效的内在逻辑，而非机械复述代码结构或组成"；名字出不出现与此无关。真实名称（包名/模块名/类名）与领域术语都可进正文，首次出现时就地绑定 `真实名称（角色，一句解释）`，此后直接使用、**不再另造第三种说法**。
  - 为何不再回避代码名：自己发明的功能角色名没有外部锚定，最容易漂移成"产品层/外壳层/装配层"；真名是最硬的身份标识，且读者进入细节时能当场对应。
  - 为何"回避代码名"曾是错的手段：一个真名都没有、却把目录结构翻译成中文，仍然是复述——换皮不改变本质。
- **正文只讲关系与因果**，不讲"这里有哪些东西"——构成已由拓扑图承担，正文不重复。故行数/文件数一类计量信息与成串构成清单不进正文。
- **名称对照表**（原"术语对照表"）角色弱化为**索引与回顾**：解释已在正文首次出现处完成，此表便于读完回顾与对应回项目检索。三列为 `名称 | 角色 | 说明`。
- **两条自检** —— 替名测试（把真实名称全替换为 A/B/C，逻辑是否仍成立：`A 取用 B 提供的能力` ✓ / `A 包含 B、C、D` ✗ 是复述组成）；重建测试（他人能否据此重建逻辑等价系统，不能的部分即下一步该展开处）。
  - 替名测试取代了原先的"删名测试"——后者建立在"正文无代码名"之上，且无法识破"换成中文角色名的构成清单"。
- **示例文件须区分元说明与导览本体** —— 以 `［示例说明］` 开头的引用块是对规则的解释，不属于导览内容；`>` 引用块专用于此，导览内容（如边语义声明）改用普通正文行。否则 agent 会把"到这里递归就结束了"这类元说明当作导览该写的话照抄。
- **拓扑是位置无关的** —— 逻辑关系不因自动布局而丢失。宏观结构之所以仍需文字，是因为它是**结论**而非图的替代。
- **示例必须虚构** —— 用真实项目当示例会导致其宏观结构被当模板套用、结论被照搬。

### 已否决的方向（避免走回头路）

- **不写探索流程 SOP**（"先读 README → 再看目录 → 再找入口"）—— 会锚定 agent，且在 monorepo/纯库/数据管道等形态上根本不成立；模型本就具备探索能力，缺的只是落点。
- **不硬分层级档位** —— 层级是观察者选定的黑箱粒度，不是项目的固有属性。
- **不使用自造术语** —— 曾出现的"三层塔""惊奇点"已删；新术语需用它消除的歧义偿付其认知成本。
- **不做渲染脚本/CLI 工具** —— 输出首先在对话中，文件非首选；渲染是前端职责（检测代码块 language tag 后解析渲染，无需工具调用）。
- **不依赖外部 mermaid skill** —— 只吸收其语法防错规则，避免破坏本 skill 的自足性。

### 拓扑绘制标准化（已完成）

统一为 **Mermaid**，避免各次调用分别用 ASCII / SVG / Mermaid。已落地：

- 绘制载体定为 Mermaid，附场景→图种**选型表**：拓扑结构 → `flowchart` + `subgraph`；交互主线 → `sequenceDiagram`；原子层状态流转 → `stateDiagram-v2`；数据实体关系 → `erDiagram`；`classDiagram` 默认不用（它罗列类与方法的清单，属于"有哪些东西"而非"如何作用"）；`architecture-beta` 暂不采用（仍为 beta，图标语义偏基础设施）。
- **语法约定**（吸收自 mermaid-syntax-skill）：节点文字一律加引号、避开保留字 `end`、注释用 `%%`、节点 ID 用完整词、`subgraph` 标题加引号。
- **一张图 8–12 节点为上限**，超出则往下分层，而非把图画大。
- **ASCII 回退**：受限于渲染端能力，如用户明确指出 Mermaid 无法渲染、或希望直接以 ASCII 展示同等含义，则改用 ASCII。
- **渲染归前端**：不调用工具、不生成图片文件。
- 示例已改为 `flowchart` + 新增 `sequenceDiagram`，用以验证选型表中"主线用时序图更清晰"这一判断。**该判断待实际使用中确认**——时序图与文字步骤存在一定重复，是否两者都保留需观察。

## 未完成项

### 1. 基线复现性验证（设计待定）

**诉求**：基线要真的"稳定复现"——同一项目在不同时间、不同 agent、不同措辞触发下，产出的导览在**结构结论上应当一致**（宏观结构认定、分块方式、关键边与关键断开），而非每次给出不同答案。措辞与详略可以不同，结构结论不应漂移。

**已获得的支撑**：小节名与字段名固定为 schema 之后，"四小节是否齐备、字段是否用原词"已成为可机检项——这是本项的第一块地基。

**待设计**：
- 判什么：结构结论的一致性，而非文字相似度。
- 怎么判：确定性检查（四小节与字段名是否齐备且用原词、Mermaid 图是否可解析、节点数是否超限）+ 语义评分（是否通过替名测试与重建测试）。
- 用什么样本：需覆盖形态差异大的项目（monorepo / 单体应用 / 无明显包边界 / 数据管道），因当前基线仅在一个 monorepo 上验证过。

> 命名说明：此项由 walkthrough 项目的 `evals/` 目录启发，但本项目讨论中的原始表述是"**基线能够稳定复现**"，而非"eval"。这里沿用原始表述，`evals` 仅为实现手段的参考。

### 2. 基线压测（进入第 2 层之前应完成）

当前基线只在一个 monorepo（包边界清晰、拓扑天然清楚）上验证过。需拿**形态明显不同**的项目各跑一遍：单体应用、无明显模块边界的项目、以数据流为主的项目。若"功能角色名 + 拓扑 + 一次完整过程"在那些项目上立不住，现在修改的成本远低于在第 2 层之上修改。

### 3. 第 2 层：重建（尚未开始）

产出"拓扑 → 局部 → 具体流"的构建指导。

**已有的承接点**：基线中的**重建测试**已是它的入口——测试暴露的缺口，正是重建指导需要补足的信息。故重建层不是另起炉灶，而是把那条自检从"判据"扩展为"产物"。

**待设计**：重建文档如何生成与编写、有哪些规范、如何组织成一段逻辑上确定的执行流。

### 4. 第 3 层：修改意图（尚未开始）

作为重建层的派生。约束已明确：**能够重建，才有资格谈论如何修改**——这天然防住了"结构没弄清就乱提改动"。

预期形态：给定一个改动意图 → 沿拓扑定位涉及的部分 → 由边关系推导影响面 → 区分"增量改动"与"架构决策" → 给出逻辑层面确定、实施层面开放的开发指导。
