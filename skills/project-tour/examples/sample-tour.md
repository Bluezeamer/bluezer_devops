# 导览：一个离线优先的笔记应用

## 一、这是什么

一个记笔记的应用。特别之处在于：**断网也照常用**——你写下的每个字都先存在自己机器上、立刻生效，等有网络时它会自动和云端对齐。多台设备改了同一篇笔记，也不会互相覆盖。

## 二、拓扑结构

> 边的语义：**数据流**（箭头表示数据往哪个方向走）

```
   你 ──写字──►┌──────────┐
               │ 编辑面板  │
   你 ◄─看到───└────┬─────┘
                    │ 每一次改动
                    ▼
               ┌──────────┐
               │ 本地仓库  │  ← 对你而言，唯一的真相来源
               └────┬─────┘
                    │ 改动记录排队
   ─ ─ ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  ← 界线：以上不知道网络存在
                    ▼
               ┌──────────┐
          ┌────│ 同步协调器│────┐
          │    └──────────┘    │
          ▼                    ▼
    ┌──────────┐         ┌──────────┐
    │ 冲突裁决  │         │ 传输通道  │
    └──────────┘         └────┬─────┘
                              ▼
                        ┌──────────┐
                        │ 云端服务  │  外部
                        └──────────┘
```

**形状**：**两个世界 + 一座桥**。界线以上（编辑面板、本地仓库）完全不知道网络的存在；界线以下负责与云端打交道；同步协调器是连接两者的唯一通道。

**一处没有连线的地方值得注意**：编辑面板与传输通道之间没有任何往来。界面永远不会因为网络慢或断网而卡住——"离线优先"这个承诺，正是靠结构上的这处断开兑现的，而不是靠某段代码里的判断。

## 三、各部分如何交互

**先看一次完整的过程**——你敲下一个字之后发生的事：

1. **编辑面板**把这次改动交给**本地仓库**。
2. **本地仓库**立刻存下来，界面立刻更新。**到这一步，对你来说这件事已经完成了**——后面的全部发生在背后。
3. 与此同时，本地仓库把"刚才发生了什么改动"记成一条记录，排进队列。
4. **同步协调器**在后台盯着这个队列，有网络时就把记录交给**传输通道**发往云端。
5. 云端也可能有别的设备传来的改动，传输通道把它们取回来。
6. 如果两边改了同一处，同步协调器请**冲突裁决**决定怎么合并。
7. 合并结果写回本地仓库，界面随之更新。

**为什么这样分是合理的**——

- **写入路径上没有网络。** 你的操作走到本地仓库就算数了，网络的事全部发生在那之后。断网可用不是一个附加功能，而是这条路径的自然结果。

- **传的是"发生了什么"，不是"现在是什么样"。** 两台设备各自改了不同段落时，两条改动记录都能保留；如果传的是"最终的样子"，后到的那份会把先到的整个覆盖掉。

- **合并规则被单独隔开。** 怎么算冲突、该保留谁，是这类系统里最容易变、也最容易出错的部分。把它单独作为一块，换一套规则不波及其他任何地方。

- **传输通道不理解内容。** 它只负责送出去和取回来，不关心送的是什么。所以换一种网络方式，同步逻辑一行都不用动。

**一个容易想反的地方**：会以为"同步"就是把本地文件上传、把云端文件下载。实际上传的不是文件，而是**一连串改动记录**；云端存的也是这些记录，而不是某个最终版本。多设备不丢东西的根本原因就在这里。

## 四、术语对照表

| 导览中的说法 | 项目/领域中的正式名称 | 一句解释 |
|---|---|---|
| 断网也照常用 | 离线优先（offline-first） | 一种设计取向：本地先成事，网络只做后台协调 |
| 改动记录 | 操作日志（oplog） | 记录"做了什么操作"，而非"结果长什么样" |
| 冲突裁决 | 合并策略 / 无冲突复制数据类型（CRDT） | 让多方各自修改后仍能自动收敛到同一结果的一类算法 |
| 本地仓库 | 本地持久化层 | 应用自己机器上的存储 |
| 同步协调器 | 同步引擎 | 决定何时同步、同步什么、冲突了找谁裁决 |
| 传输通道 | 网络客户端 | 只负责数据的收发 |

# 向下展开一层：冲突裁决

> 演示两件事：子节点同样由四部分构成；以及当一块**画不出拓扑**时该怎么办。

## 一、这是什么

当两台设备改了同一处，它负责决定最终应该是什么样——并且要保证：**不管两边的改动以什么顺序传到、传几次，各台设备最后得到的结果都完全一致。**

## 二、拓扑结构

**画不出来——它不由几个部分构成。** 它是一段单一连贯的判断逻辑，没有内部分工，也就没有边可画。

**到这里递归就结束了。** 这时该讲的不再是"由哪些部分如何协作"，而是"它用什么办法做到"。

## 三、它用什么办法做到

思路是：**让每一次改动都自带足够的信息，使得"谁该赢"是一个所有设备都能各自算出同一答案的问题，而不需要谁来当裁判。**

- 每条改动记录都带上"是谁改的、改的是哪个位置"这样的标记。
- 两条改动碰在一起时，按一套**所有设备都遵守的固定规则**排出先后——比如按标记的大小排。规则本身不重要，重要的是它对所有设备都一样、且不依赖谁先收到。
- 因此无论改动以什么顺序、重复几次到达，算出来的结果都相同。这就是"最后一定一致"的来源。

代价是：结果**一定一致，但不一定符合人的预期**——两个人同时改同一句话，机器只能挑一个赢，它没法理解哪个更有道理。所以这类系统通常还会在别处保留一份历史，让人能翻回去看。

## 四、术语对照表

| 导览中的说法 | 正式名称 | 一句解释 |
|---|---|---|
| 所有设备各自算出同一答案 | 收敛性 | 不同副本独立计算，最终得到相同状态 |
| 不管顺序和次数结果都一样 | 交换律与幂等性 | 换顺序不影响结果；同一条重复应用也不改变结果 |
| 是谁改的、改的哪个位置 | 副本标识与逻辑时钟 | 用于给并发改动定序的标记 |
