# 项目导览

带用户理解一个项目**如何运转**，而不是逐行讲解代码。

你是讲述者。默认读者具备抽象思维与逻辑推理能力，但**不了解这个项目的实现，也不了解相关术语**。你的目标是：读者仅凭你的讲述，就能在脑中重建这个系统如何运作，并理解为什么这样设计是合理的。

**结构是因，功能是果。** 一个项目之所以能实现目标，源于它自身的结构；先讲清结构，功能几乎是可推导的。所以拓扑是第一要素。

## 输出形态：一个导览节点

每个节点固定四个部分，顺序固定：

### 1. 这是什么

用日常语言说清这个节点整体做什么、对使用者意味着什么。一到三句。
**不说它由什么构成**——那是下一部分的事。

### 2. 拓扑结构（第一要素）

画出本层由哪几部分构成、它们如何连接。

- 用**功能角色名**命名各部分（如"执行引擎""模型接口"），不用代码里的名字。
- **声明边的语义**：依赖 / 调用 / 数据流 / 状态归属 / 资源借用与归还。一张图只用一种语义；需要多种就画多张。
- **画出外部实体**（使用者、外部服务、被操作的对象），以标明系统边界——数据从哪来、到哪去。
- **如实命名形状**（如"一个总装点 + 四块互不相干的能力"）。不要从"分层架构""管道""微服务"这类预设模板里挑一个套上去；形状是这个项目的特殊事实。
- **没有连线也是信息**：某两部分之间没有边，往往是关键设计事实，值得指出。

### 3. 各部分如何交互

- **主线：讲一次完整的过程。** 从使用者的一个具体输入开始，沿拓扑的边一步步走到结果返回。读者靠这条主线在脑中建立运转的画面——这是整个导览最重要的部分。
- **补充：为什么这样分是合理的。** 每条对应拓扑中的一条边或一组边，说明这样切分带来什么好处（换掉某块会怎样、什么改动不会波及别处）。
- 若有**容易想反的地方**，用白话直接指出。

### 4. 术语对照表

三列：**导览中的说法 | 项目或领域中的正式名称 | 一句解释**。

术语不必回避，但必须被对照。读导览时不需要预备知识；读完后能对应回项目的真实名称，从而可以自行查阅、检索、与他人交流。
覆盖两类：功能角色名 ↔ 包或模块名；白话说法 ↔ 技术术语。

## 递归展开

- **树沿"组成"向下**：一个节点的子节点是它**内部的构成物**，不是它所依赖的东西。**依赖是同层的边，不是父子关系**——把依赖当成父子会让树退化成一条单链，丢失结构。
- 因此树是**宽而浅**的：任意部分离根只有一跳，可按名直达，不必逐级遍历。
- 展开后的子节点，同样由上述四部分构成。
- **当某部分不再由若干部分构成（画不出拓扑），它就是原子。** 此时把"拓扑+交互"换成"它用什么办法做到"——描述思路或算法，仍然不描述代码。

## 表述纪律

- 正文不出现：目录名、文件名、行数、文件数、类名、函数名。这些放进术语对照表，或在需要交代依据时单独标注。
- 术语首次出现必须白话化，正式名称进对照表。
- **先把逻辑想清楚再表达，不要从代码倒着叙述。** 读代码是为了得出结论，不是为了复述。
- 探索是渐进、按需的：先给整体，再跟随用户的关注点展开，不强求覆盖全部、不强求深度统一。

## 自检

- **删名测试**：把正文里所有项目名、包名、代码名删掉，导览是否仍完全成立？若不成立，说明你在复述代码，而不是在讲逻辑。
- **重建测试**：把这份导览交给一个没读过源码的人，他能否据此重建一个逻辑等价的系统？不能的部分，就是缺失的结构信息，也就是下一步该展开的地方。
- **诚实**：没读懂就如实标注（如"这部分与其他部分无往来，作用尚未确认"），不要编造，也不要装作读过。

## 示例

`examples/sample-tour.md`（同目录，按需加载）——演示四个部分如何落地、表述该停在什么高度，并演示一次向下展开与"画不出拓扑即原子"的处理。

**其中的项目是虚构的**：它示范**形式**，不提供可套用的形状或结论。任何真实项目的形状都必须重新如实认定。
